## How the agent was used as a specification agent

- The four documents (`specification.md`, `api-spec.md`, `ui-spec.md`, `tests.md`) were committed and reviewed in PR #71 **before** any implementation branch existed, with the Actions Taken fields, the status matrix and the authorization matrix as tables so that each cell could become a test row, and every acceptance criterion traced to at least one planned test.
- The agent corrected the contract when the build disagreed, in small visible commits: BR-04 now counts characters instead of UTF-16 units (a review comment on #72), an empty edit is a `400` (found while writing a test), and `myRecentActions` is defined as Actions *performed by* the signed-in user (a review comment on #75).
- Anticipated-review drafts (what a reviewer might ask) were kept in the course vault, not in the repository. Their relation to the reviews on GitHub is stated plainly in "Where the review comments on #71–#78 came from" below.

## How the agent was used as a coding agent

- **Test-first for the API:** 46 of the new API tests failed before the Actions routes existed (L4-2), and the gate and stale-update tests were written red before the code (L4-3). Some tests were written together with the code and say so in their PR notes (for example the pure validation tests in L4-2).
- **A create-only migration with evidence:** the Actions table was added without altering anything existing; the agent followed the recovery steps in the migration header on the real local data (drop, re-apply) and recorded identical row counts before and after, and an empty drift check.
- **Concurrency tests that force the overlap:** the tests hold the Ticket row lock themselves, wait until both requests are queued behind it, then release it. API-13 first passed without any lock, which showed the test was not testing the lock; it was rewritten and then checked by removing the lock on purpose.
- **Mutation checks as the habit:** for almost every test group the agent removed the code under test, watched the named tests fail, and restored it. Examples are in each PR description.
- **Tests caught real defects in the agent's own work** (each fixed in its own commit, listed in `reviewer.md`): a status choice wiped by a refresh (L4-3), "New action" still enabled after a ticket was resolved, Reload that left the comments stale, and My Tickets still printing raw status codes (found by the E2E suites in L4-7); and the agent's own tests had errors that were found and corrected (an oracle that compared UTC with local time, a keyboard test that walked the date field wrongly, an "obsolete UI" check that matched ticket content).

This section was added after the review of PR #78 pointed out that the earlier wording of this document implied that a second person found the problems. What can be checked, and what cannot:

## My Reflection

> **Who wrote this section.** The AI agent drafted this reflection from the record of the sprint (the commits, the pull requests and the review comments), as the agent did for Lab 3. It is the agent's account, written in the first person of the agent, not my own prose. The list "What stayed mine" at the end is the one part that records my decisions. I will read and edit it before submitting if the course requires my own words.

**As a specification agent (written by the agent).** Writing the contract before the code was worth it: nearly every PR could be reviewed against a named rule (BR-19, AC-24, D-09) instead of against the reviewer's memory of what I meant. The three contradictions in the handout were the most useful thing the first hour produced, because deciding them on paper meant no later argument about what "resolved" means. The weakness was that the spec described the happy path of each rule more carefully than the interactions between rules. Examples named by review comments: a retry with the same `requestKey` but different text silently loses the correction (BR-16 against BR-33), and the 30-day card and its list are evaluated at different moments (AC-31), which I had to add to the known limitations.

**As a coding agent.** What made my work trustworthy was evidence rather than the word "done": tests red before code, a lock removed on purpose to prove its test can fail, row counts before and after a migration, and a real browser run. What did not hold up was the idea that this is enough. In L4-7 I wrote a change that contained a real defect, which a review comment on #77 pointed out: when I made the Actions panel refetch (to fix a bug the E2E suite found), an open edit form started to send the *newest* `version` instead of the one the user saw, so a save could overwrite another person's change without the stale warning. Every test was green, because no test refreshed the list while a form was open. The review comment found it by reading the code with a different question; who first asked that question is not established by this record (see above). That is the clearest lesson of the lab: green tests prove what was thought of, and a fix needs the same adversarial reading as new code.

**What went wrong in the process, specifically mine.** I merged PRs #73–#77 after confirming only that GitHub showed them approved and mergeable. The approvals came with inline comments that named real defects (a lost correction on retry, the seconds of a time being rewritten by an edit, an empty filter value treated as "no filter", dashboard links smaller than a touch target, and the stale-version bug above). I read them only afterwards, when I gathered the material for `reviewer.md`, and fixed them together in L4-8. Approval is not the same as "nothing left to do", and the instruction to merge on approval should have come with a step of mine: read every comment first and say which ones need a fix before merging.

**Things that did not work or that I would do differently.** Writing a long self-review checklist did not replace an independent reader. The intermittent 60-second E2E stall seen in L4-2 to L4-6 was disclosed in four PRs and is still unexplained; I kept a trace on failure for the next time, but I cannot claim it is fixed. Running the whole E2E suite twice at once (a background run and a foreground run) left test users behind and made two Lab 3 tests fail for a reason that had nothing to do with the application; the cleanup and the rerun are noted in `tests.md`. And the first version of several of my own checks was wrong before it was right (UTC against local time, the keyboard walk of a date field, the obsolete-UI scan), which is a reminder to test the test.

**What stayed mine (the student's).** I set the deadline and the workflow ("ตามเดิม"), approved the decisions D-01 … D-15 in the specification, decided which step reached GitHub and when (each "push แล้วเปิด PR L4-n", each approval and merge), required that Issues move to In review automatically and to Done on merge, and ruled out AI attribution lines in PR text. The evidence for Parts 1–9 (real runs, screenshots, the review record) is kept as the proof, because "the agent said it passes" is not evidence.
